# 同一Skill的维护流程

## 出现新问题时

1. 收集最小复现：打开方式、视口/DPR、实际工具响应或失败请求、截图位置。不要只记录“像不像”。
2. 先分层：来源不足、实现遗漏、包装路径、字体文件/映射、绘制/色彩，还是经过证据确认的引擎差异。
3. 用原创合成页面或用户允许的脱敏材料建立回归。公开测试不得包含真实Figma文件标识、截图、原字体、本机路径、临时URL或凭据。
4. 修改最窄的脚本/规则：通用错误进入检查门；环境问题进入条件说明；设计参数留在该项目，不写成所有项目默认。
5. 运行相应回归、Skill结构检查、包内容检查。只有实际运行过的检查才能写通过。
6. 同步版本、CHANGELOG、安装包；发布按当次用户授权。相同Skill名和仓库保持稳定，不把版本号或“学生试跑”放进项目名。

## 本地检查

```bash
python3 -m unittest discover -s tests -v
node --check scripts/verify_delivery.mjs
```

浏览器集成回归：

```bash
node tests/browser_regression.mjs --channel chrome
```

macOS仍遵守宿主的浏览器启动权限规则。脚本不复用日常profile。集成回归使用合成素材，验证正常包、丢图、后备字体、叠图权重、三种打开方式下的多状态链路、错误返回与跳转后资源是否正确判定，不把这些结果当成真实Figma还原或学生使用效果。

仓库当前未启用GitHub Actions。需要CI的维护者可参考[检查配置示例](ci-checks.example.yml)，在有相应仓库权限时自行配置；示例文件本身不会执行工作流。

## 发布前

只从此独立仓库打包与提交，不能从包含真实课程和设计产物的上级目录直接git add。包内不放学生素材、字体文件、浏览器profile或测试生成物。Skill结构检查通过不等于行为正确；回归结果、截图实际检查和学生反馈分别记录。
